
On a first try, `opt/lib/x86_64-w64-mingw32/lib/libelf.a`, was **not**
actually built for the intended mingw target: the archive's object files were
native Linux ELF64, and its bundled `sys_elf.h` had been generated by
`configure` on the Linux host (`#define __LIBELF_HEADER_ELF_H <elf.h>`,
which does not exist for mingw). All the other static libraries in `opt/lib`
(libusb, libusb-1.0, hidapi, libftdi1, libconfuse, ncursesw, libxml2) were
correctly built as Windows COFF objects — only `libelf` was affected. This
section documents how we fixed the build.

Source used: `libelf-0.8.13` (Michael Riepe's libelf, the same version
avrdude's own `CMakeLists.txt` FetchContent path — `USE_EXTERNAL_LIBS` —
would otherwise pull from `github.com/avrdudes/libelf`), extracted from
`libelf-0.8.13.tar.gz`.

### Why `--host=x86_64-w64-mingw32` doesn't work

`libelf-0.8.13`'s `configure` script predates `AC_CANONICAL_HOST`/
`AC_CANONICAL_SYSTEM` — `configure.in` calls plain `AC_PROG_CC` and nothing
else host-related. The generated `configure` still *parses* `--host=...`
(every autoconf script does, for `install-sh`/`config.sub` compatibility),
but the value is only used to set inert `host`/`host_cpu`/`host_os` shell
variables — it never prefixes the compiler search (no
`ac_tool_prefix=${host_alias}-` pattern) or otherwise changes which
compiler `AC_PROG_CC` picks. So `--host=x86_64-w64-mingw32` is silently a
no-op, and `AC_PROG_CC` just finds the native Linux `gcc` on `$PATH` — hence
the native-ELF64 library that resulted.

The fix for that part is simple: don't rely on `--host` at all, just set
`CC`/`AR`/`RANLIB` directly to the cross tools before running `configure`
(`AC_PROG_CC` in this script uses `$CC` as-is when it's already set in the
environment).

### Two more problems that surface once `CC` is set correctly

1. **`main(){return(0);}` no longer compiles.** `configure`'s own compiler
   sanity check links this K&R-style test program (implicit `int` return,
   no prototype). Clang (llvm-mingw is clang-based) now treats
   `-Wimplicit-int` as an error by default in C17/C99 mode, so the check
   fails with `configure: error: installation or configuration problem:
   C compiler cannot create executables.` — even though the compiler itself
   is fine. Fix: pass `CFLAGS=-std=gnu89`, which restores the old implicit-int
   behavior as a warning instead of an error.

2. **The `conftest` executable-name check doesn't account for `.exe`.**
   This script also predates `AC_EXEEXT`: it links test programs with
   `-o conftest` and then does `test -s conftest` to check the link
   succeeded. mingw-gcc always appends `.exe` to linker output regardless of
   the `-o` name given, so the real output is `conftest.exe` and the bare
   `conftest` never exists — the same "cannot create executables" error,
   this time despite both the compiler *and* the test program being fine.
   Fix: a small wrapper, `scripts/mingw-conftest-wrapper.sh`, that runs the
   real compiler and then copies `<name>.exe` to `<name>` when the caller
   asked for `-o <name>` without an extension. This only ever fires for
   linked executables (never for `-c` object compiles), so it's harmless to
   leave in place for the actual `make` build too.

   (Once past this check, `configure`'s cross-compiling autodetection *does*
   work correctly on its own: it tries to run the linked `conftest` and,
   since a `.exe` can't execute directly on this Linux host — no `binfmt_misc`
   handler for PE registered — it falls through and correctly concludes
   `cross_compiling=yes`.)

### Sizeof/mmap guesses under cross-compiling

With `cross_compiling=yes` correctly detected, this old configure script
skips every runtime-executed check (`AC_TRY_RUN`) and falls back to
hardcoded default guesses. These happen to already be correct for Windows'
LLP64 data model: `sizeof(short)=2`, `sizeof(int)=4`, `sizeof(long)=4` (unlike
Linux x86_64's LP64, where `long` is 8 — this only works out because
autoconf's ancient cross-compiling defaults assume a 32-bit-ish target).
`sizeof(long long)` and `sizeof(__int64)` both default to `0`, so libelf's
`configure.in` can't find a native 64-bit integer type and disables
`__LIBELF64` (64-bit ELF struct/function support, i.e. `elf64_*`/`gelf_*`).
This is fine here: avrdude only ever calls `elf32_*` (AVR is a 32-bit
architecture; see `avrdude-8.2/src/fileio.c`), so no 64-bit ELF support is
needed. `AC_FUNC_MMAP` similarly defaults to "not working" when
cross-compiling, which just makes libelf use its non-`mmap` I/O fallback —
also fine, and arguably more portable for a Windows target regardless.

### Reproducing the libelf build

```bash
TOOLCHAIN=opt/llvm-mingw-20251216-msvcrt-ubuntu-22.04-x86_64/bin
WRAP=scripts/mingw-conftest-wrapper.sh

cd libelf-0.8.13
MINGW_CC_REAL=$(pwd)/../$TOOLCHAIN/x86_64-w64-mingw32-gcc \
CC=$(pwd)/../$WRAP \
CFLAGS="-std=gnu89" \
AR=$(pwd)/../$TOOLCHAIN/x86_64-w64-mingw32-ar \
RANLIB=$(pwd)/../$TOOLCHAIN/x86_64-w64-mingw32-ranlib \
./configure --prefix=/tmp/libelf-install

MINGW_CC_REAL=$(pwd)/../$TOOLCHAIN/x86_64-w64-mingw32-gcc \
make CC=$(pwd)/../$WRAP \
     AR=$(pwd)/../$TOOLCHAIN/x86_64-w64-mingw32-ar \
     RANLIB=$(pwd)/../$TOOLCHAIN/x86_64-w64-mingw32-ranlib

MINGW_CC_REAL=$(pwd)/../$TOOLCHAIN/x86_64-w64-mingw32-gcc \
make install CC=$(pwd)/../$WRAP \
     AR=$(pwd)/../$TOOLCHAIN/x86_64-w64-mingw32-ar \
     RANLIB=$(pwd)/../$TOOLCHAIN/x86_64-w64-mingw32-ranlib
```

This installs, under `/tmp/libelf-install`:

```text
lib/libelf.a
include/libelf.h, gelf.h, nlist.h                 (forwarding stubs)
include/libelf/libelf.h, gelf.h, sys_elf.h, nlist.h, elf_repl.h
lib/pkgconfig/libelf.pc
```

Copy `lib/libelf.a` and everything under `include/` into
`opt/lib/x86_64-w64-mingw32/{lib,include}` respectively (this matches the
layout already used by the other prebuilt libraries there). Verify the
result is real mingw COFF, not host ELF, before trusting it:

```bash
ar x opt/lib/x86_64-w64-mingw32/lib/libelf.a --output=/tmp/libelf-objcheck begin.o
file /tmp/libelf-objcheck/begin.o
# expect: "Intel amd64 COFF object file" -- NOT "ELF 64-bit LSB relocatable"
```

Configure and build avrdude as in steps 2–3 above (no `HAVE_LIBELF`
override needed); the configure summary should show `DO HAVE    libelf`,
and `check_include_file(libelf.h HAVE_LIBELF_H)` should succeed.
